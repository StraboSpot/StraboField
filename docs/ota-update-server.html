StraboField · over-the-air updates

Hosting StraboField's update server

StraboField is adding over-the-air (OTA) updates so JavaScript bug fixes reach phones without an App Store or Play Store release. The app side is done. It needs an HTTPS endpoint on our server that speaks the Expo Updates protocol (version 1). This page is everything the server side has to do.

What happens on a phone

  1. The app launches straight away from the JavaScript bundle it already has. It never waits for the network.
  2. In the background it sends one GET to the update URL, saying which platform it is and which native build (runtime version) it is.
  3. The server replies with the newest update for that platform and runtime version, or says there is none.
  4. If there's a newer update, the app downloads its files and verifies their hashes. It starts using them the next time it's opened.
  5. If a new update crashes on launch, the app falls back to its previous working bundle on its own.

Geologists often work with no signal, so a request may fail or arrive days late. The app copes with that, and the server needs no special handling for it.

1. The manifest endpoint

One URL, for example https://strabospot.org/ota/manifest (the exact path is yours to choose). The app sends a GET with these headers:

Request headerMeaning
expo-platformios or android
expo-runtime-versionFingerprint of the installed native build, a 40-character hex hash. Only serve updates published for exactly this value.
expo-protocol-version1
acceptmultipart/mixed,application/expo+json,application/json
expo-current-update-idUUID of the update the phone is running now
expo-embedded-update-idUUID of the bundle that shipped inside the store build
eas-client-idRandom per-install ID. Useful for counting devices and for staged rollouts. Not tied to a user account.
expo-fatal-errorOnly sent after a crash: the error that made the app roll back (up to 1,024 characters). Worth logging.
expo-expect-signatureOnly sent when code signing is on (see section 4)

Responses

CaseReply
No update for this platform and runtime version204 No Content
An update exists200, content-type: multipart/mixed, with a part named manifest (JSON, below) and optionally a part named extensions
Roll everyone back to the store build's bundle200 multipart with a part named directive: {"type":"rollBackToEmbedded","parameters":{"commitTime":"<ISO date>"}}

Every 200 response also carries expo-protocol-version: 1, expo-sfv-version: 0 and cache-control: private, max-age=0. Never let a proxy or CDN cache the manifest response. Each part's headers are content-disposition: form-data; name="manifest" and content-type: application/json; charset=utf-8.

Manifest JSON

{
  "id": "6f1c3a2e-9b0d-4c55-8a7e-2d1f0b9e4c11",
  "createdAt": "2026-11-20T18:04:11.000Z",
  "runtimeVersion": "8a7a06b7cbdf40f10d16002bae0d61219d60cac8",
  "launchAsset": {
    "hash": "Xb9Q3...base64url SHA-256...",
    "key": "c1e5...md5...",
    "contentType": "application/javascript",
    "fileExtension": ".bundle",
    "url": "https://strabospot.org/ota/assets/ios/8a7a06b7.../index-c1e5.hbc"
  },
  "assets": [
    {
      "hash": "pN2k...base64url SHA-256...",
      "key": "4b2f...md5...",
      "contentType": "image/png",
      "fileExtension": ".png",
      "url": "https://strabospot.org/ota/assets/4b2f..."
    }
  ],
  "metadata": {},
  "extra": { "expoClient": { "...": "contents of npx expo config --type public" } }
}
  • id is a UUID unique to each published update. Two different updates must never share an ID.
  • hash is the file's SHA-256, encoded as base64url with no padding. The app rejects any download that doesn't match.
  • key identifies the file (its MD5 hex works well). The app skips downloading any asset whose key it already has.
  • launchAsset is the JavaScript bundle, compiled to Hermes bytecode (.hbc). It's about 9 MB per platform.

2. Asset files

  • Plain static files over HTTPS, at the URLs the manifest lists. A CDN or a static directory behind nginx is fine.
  • They never change once published: a new update means new files at new URLs. They can be cached for a long time (cache-control: public, max-age=31536000, immutable).
  • Serve them with the contentType the manifest gives them. Supporting HTTP range requests is a plus, not required.
  • The app sends no authentication. If assets need a token, the app can be configured to send fixed extra headers, so tell us.

3. Publishing an update

On our side, publishing means running npx expo export and sending the server its output. Each publish hands over:

  • The dist/ folder. Its metadata.json lists, for each platform, the bundle path and every asset with its file extension. The bundles are under _expo/static/js/<platform>/ and the assets under assets/.
  • The runtime version for each platform. These are separate fingerprints for iOS and Android, and an update must only be offered to the matching one.
  • The public app config (npx expo config --type public), which goes into extra.expoClient.

The server should store each publish under its platform and runtime version, compute the hashes and keys, and answer manifest requests with the newest one. A layout like updates/<runtimeVersion>/<timestamp>/ is enough. Keep older publishes so we can roll back.

We need some way to upload a publish. That could be an authenticated upload endpoint, or rsync/scp to a directory the server watches. Whichever is easier for you.

4. Code signing (strongly recommended)

Whatever this server sends runs as code on every phone that has the app. If the server or its storage were compromised, an attacker could push code to all of our users. Code signing closes that gap: the app is shipped with a certificate and refuses any manifest that isn't signed by the matching private key.

  • We generate the key pair (npx expo-updates codesigning:generate) and build the certificate into the app.
  • When a request includes expo-expect-signature, the server signs the manifest part's exact bytes with RSA-SHA256. It adds the signature to that part as an expo-signature header: a structured-header dictionary with sig (base64) and keyid ("main").
  • Keep the private key out of the web root and out of the repository. Better still, sign at publish time and store the signature with the manifest, so the running server never holds the key.
Code signing has to be in place before the first store release that points at this server. Adding it later needs another store release.

5. Rollback and rollouts

  • Bad update: mark it withdrawn, and the server answers with the previous publish (republished under a new id). To go back to the bundle that shipped in the store build, send the rollBackToEmbedded directive.
  • Beta testers first (optional): the app can send a fixed header such as expo-channel-name: beta, set at build time, and the server serves that channel's newest update. A staged rollout can also hash eas-client-id into buckets.

6. Load and operations

  • One small manifest request per app launch per device. Most of them get 204.
  • Downloads happen once per device per update: about 9 MB of bundle plus any changed images.
  • HTTPS with a valid public certificate is required. iOS refuses plain HTTP and self-signed certificates.
  • Useful logs: requests per runtime version and platform (shows which builds are still in use), and any expo-fatal-error values.

Starting points

  • Protocol spec: docs.expo.dev/technical-specs/expo-updates-1
  • Expo's reference server (Node/Next.js), which implements all of the above including signing: github.com/expo/custom-expo-updates-server. It's small enough to port to whatever our server already runs.

What we need back

  • The final manifest URL. It gets built into the app.
  • How we upload a publish: an endpoint or a directory.
  • Whether you'll sign at request time or at publish time, so we know where the private key goes.
  • Whether you want a beta channel from day one.
